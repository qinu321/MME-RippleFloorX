RippleFloorX 技术文档
======================================================================

  这份文档是给「要改这个效果的人」看的：原理、状态纹理布局、形状数学、
  全部可调参数、调试色带、构建与校验方法、版本史与踩过的坑。
  终端用户只需要看 readme.txt。


【工作原理】

  子效果（RF_FootRipple.fxsub，给每个 PMD/PMX 自动挂）：
    脚接触地面时，往「离屏渲染目标」底部写一个 4x4 像素小方块，
      颜色 = (地板局部 x, 地板局部 z, 0, 接触中 = 1)
    不接触就把方块收缩成零点，什么都不写。缓冲区每帧被 MME 自动清空，
    所以方块只在该脚真的踩地时存在。

  地板（RippleFloorX.fx）：
    每帧读 16 个脚位（= 8 个模型对 × 左右），判断「这一帧有没有新的一步」，
    有就往队列头部插一条 (x, z, 起始时间, 1 + 图案编号)，
    然后在地板平面上把队列里的环画出来（自己扩散、衰减、旋转）。

  .x 里声明了 OFFSCREENRENDERTARGET，其 DefaultEffect 把 *.pmd/*.pmx 都指向
  RF_FootRipple.fxsub，所以换角色不用改任何文件。


【状态纹理（1 x 32, RGBA32F）】

  行  0 - 24   涟漪队列（25 槽）
  行 25 - 27   每个模型对的上次出环时刻（.rgb 三个一对：对 0,1,2 / 3,4,5 / 6,7）
  行 28 - 30   每个模型对的上次出环中点（同样三分法，用来判「滑步」）
  行 31        脚部位掩码：第 f 位 = 槽位 f 上一帧是否踩在地上（读 .w）

  上一帧状态用 TEXTUREVALUE 取：MME 在帧首把整张纹理塞进常量寄存器，
  32 个 texel 在限制内，所以没有双缓冲、也没有拷贝 pass。

  !! 写入规则（改这个效果前务必读）!!

  往这张纹理写一行时：**写进去的 alpha 是 0，整行都读不回来** ——
  不是只丢 alpha，是四个通道一起读回 0。

  证据（1.6~2.8 十几轮全栽在这里）：
    · 同一行、同一个 pass、同一个值，写进 .w（那一行 alpha 恰好是 1）能读到 1，
      写进 .x（那一行 alpha 恰好是 0）读回来是 0。
    · 2.6~2.8 把「每对模型的冷却时刻 / 上次落点」四个一对塞进一行，alpha 就成了
      「第 4 对的冷却时刻」。只载 1 个模型时它恒为 0 ⇒ 整行丢失 ⇒ 冷却读回 0
      （永不生效）+ 落点读回 decode(0) = (-64,-64)（滑步判定永远成立）
      ⇒ 站着不动每 0.4 秒冒一圈 = 「疯狂冒」。
    · 队列行一直正常，因为它的 alpha 是 1 + 图案编号，从来不是 0；它的 .xy
      一直读得对（环确实落在各自脚下）—— 所以「.x 通道坏了」这个旧结论是错的，
      差别在 alpha，不在通道。

  规矩：**每一行的 alpha 必须 ≥ 1**；一行只放 3 个 payload（.rgb），
  第 4 个值宁可另开一行也不要塞进 .a；掩码行四通道同值、读 .w 也守这条。
  另外 UpdateState pass 显式写了 ALPHATESTENABLE = FALSE / COLORWRITEENABLE = 0xF，
  不继承 MMD 遗留的渲染状态。


【触发规则（v2.9 起）】

  fire(pair) = cnt > 0 && (edge || slid) && cooled

  edge    该对任一在踩的脚「上一帧没踩、这一帧踩」（落地沿）
  slid    cnt > 1 且（两脚中点 vs 该对上次出环中点）距离 > StepLen()
          且上次中点必须可信（HasPoint：落点在 ±40 内，否则当作没有记录）
  cooled  该对距上次出环 > TriggerGap()

  要点：
  · 滑步必须用「两只脚的中点」，不能拿单个脚去和另一只脚的落点比：
    左右脚相距 5~8 单位，那样比会让两只脚轮流「滑步」，站着不动也一直出环。
  · 滑步只在**两只脚都踩地**时判定（cnt > 1）：单脚支撑时「在踩脚的中点」
    会塌到站立那只脚下，看起来就像滑步。单脚动作靠落地沿出环。
  · cooled 是**按模型对**算的（v2.4 起）。以前全场景共用一个节流，5 个模型
    互相抢，只有一个模型脚下出特效、还会轮流。
  · 一帧最多入队 8 条（每个模型对一条）：多人对齐帧数很容易，队列插入按
    「这一帧有几对触发」整体前移，同帧落地全部保留。


【五种图案与形状数学】

  图案编号存在队列条目的 .w 里：alpha = 1 + type（所以恒 ≥ 1）。
    type 0 放射线（1.5 秒内淡出，不随时间旋转）
    type 1 旋转三角形
    type 2 旋转正方形
    type 3 圆
    type 4 五角星
  ptype = fmod(floor(CurTime) + 模型对编号, 5) ⇒ 5 秒一轮、不同模型错开。

  1) 正 n 边形（三角/方）：用「边心距等值线」
       w = r * cos(offset)，offset = fmod(|θ|, 2π/n) − π/n
     等值线 w = A 就是边心距 A 的正 n 边形。

  2) 尺寸归一化（v3.0）：n 边形的外接半径 = A / cos(π/n)（三角 2.0、方 1.414、
     圆 1.0）。要「换图案时环不忽大忽小」，把比较基准先乘 cos(π/n)。
     ⇒ 副作用：三角/方看起来比 v2.9 小一圈，这是刻意对齐，不是画错。

  3) 五角星（v3.0）：不能用上面的等值线（非凸会自交），改用「谷→尖的直弦」
     的极坐标式：
       φ = |fmod(|θ|, 72°) − 36°|                     （0 在谷，36° 在尖）
       den = (inr − cos36°)·sinφ + sin36°·cosφ
       r(φ) = r_inr·sin36° / den                       （直弦的极坐标形式）
       w = r · den / (inr · sin36°)
     反面教材：按角度在谷半径与尖半径之间线性插值 ⇒ 得到的是「花瓣/扇面」，
     不是星形（笛卡尔空间里是曲线）。这类错误读代码看不出来，必须渲一张图。

  4) 线宽补偿（v3.4）：图形用 w = f(r,θ) 定义时，**垂直于边的实际线宽
     = 带宽 / |∂w/∂r|**。方形/三角的 |∂w/∂r| 在 0.5~1 之间，星形在
     1/STAR_INNER ≈ 3.33（谷）到 1（尖）⇒ 星形谷部只有三角的约 1/4 粗。
     解法：星形分支里取 k = |∂w/∂r|，把 w、带宽、AA 半宽一起乘 k，使线宽成常数；
     再乘 STAR_BAND_MUL 1.25 补回「星形天生显得轻」的视觉分量。
     实测线宽（scl=8、RIP_BAND=0.04、垂直边）：圆 0.32 / 三角 0.32~0.64 /
     方 0.32~0.45 / 星旧 0.144 / 星新 0.40。

  5) 图案总数决定循环周期：5 种 ⇒ 5 秒一轮。加形状会稀释「每步换一个样子」。

  !! 不要再加「短命爆发」类图案 !!（v3.1 试过「花瓣爆开」：1.6 秒、自带中心
  闪光、ease-out 扩张，v3.2 删除）。它与这套 5 秒匀速扩散的环不是一个节奏，
  观感不搭。新图样只做「同一个环、换轮廓」（像五角星那样）。

  出生 0.15 秒内淡入，越往外越淡（1 / (1 + 半径×0.22)），最后 1.5 秒整体淡出，
  叠加值上限 1.6。


【多模型分槽（16 脚位 = 8 个模型对）】

  cx = floor(センター.x / CENTER_BUCKET)      ← 主判据（摆位在这里）
  cz = floor(センター.z / CENTER_BUCKET)
  rx = floor(全ての親.x / ROOT_BUCKET)        ← 补判据（通常恒为 0）
  rz = floor(全ての親.z / ROOT_BUCKET)
  pair = (VertexCount/8 + SubsetCount + cx + 3*cz + rx + 3*rz) % 8
  slot = pair * 2 + 左/右

  · 不同模型：VertexCount / SubsetCount 不同，自然分开。
  · 同一个 PMX 载多份：只能靠摆位分。多人摆位惯例是给 センター 打偏移关键帧。
  · 「全ての親」只当补判据：正经动作里它通常恒为 0，贡献 0、不干扰主判据；
    只有两份模型的 センター 落进同一粗桶时才靠它分开。
  · 两轴都参与（Z 权 3），横排纵排都能分开。
  · 桶宽：センター 32 单位（抗动作摆动）；全ての親 8 单位（细，它本来不动）。
  · 最多 8 个模型，超过会循环复用槽位。撞槽就调 CENTER_BUCKET 或把模型拉开。
  · 同一动作载给多份时，动作对两根骨的位移相同 ⇒ 相对分桶不变，不会撞槽。


【队列预算】

  25 槽 × 寿命 5 秒 ⇒ 全场可持续约 **5 条/秒**。

  1 个模型跳（约 2 条/秒）：富余，环都能活满 5 秒。
  8 个模型按默认 0.4 秒间隔 = 20 条/秒：超载 4 倍，环被大量挤掉。
      ⇒ 多人把 Freq- 拉到 0.25 以上（间隔 1.6 秒 ⇒ 全场 5 条/秒打平），0.4~0.5 舒适。
  5 个模型约 10 条/秒：饱和，实际寿命约 2.5 秒（每个模型都有环，只是短）。
  想更密：把 RIP_MAX 调小（→3 秒 ⇒ 可持续约 8.3 条/秒）。
  想全都活满：把 TRIG_GAP 调到 0.9~1.2。

  状态纹理只有 32 行：队列 25 + 每模型状态 6 + 掩码 1，已占满。
  再想加长队列必须开第二张状态纹理（并改 TEXTUREVALUE 数组与行号）。


【全部可调参数】

  RippleFloorX.fx 顶部：
    RIP_MAX       5.0    涟漪寿命（秒）；Life± 缩放它
    RIP_RADIUS   16.0    寿命结束时的半径（地板局部单位，地板 ±10）
    RIP_BAND      0.04   线条粗细（半径的比例）
    RIP_LINE_W    0.15   放射线图案的线宽（局部单位）
    RIP_ROT       4.0    图案基础旋转速度（弧度/秒）；Rot± 缩放它
    STAR_INNER    0.45   五角星内凹半径比（调小=角更尖长）
    STAR_BAND_MUL 1.25   五角星线宽倍率（等宽会显得比方形轻）
    ROT_GAIN      1.5    Rot± 拉满时的倍率（×2.5 / ÷2.5）
    SIZE_GAIN     1.5    各 Sz± 拉满时的尺寸倍率（×2.5 / ÷2.5）
    JITTER_AMP    0.25   Jitter 拉满时每条涟漪的尺寸摆动（±25%）
    SLOT_COUNT     25    队列槽位（行 0-24）
    MASK_ROW       31    脚部掩码行
    SLOT_MAX       16    脚位槽数，须与 fxsub 的 FOOT_SLOTS 一致
    TRIG_GAP      0.40   每模型两次出环的最小间隔（秒）；Freq± 缩放它
    FREQ_GAIN_P   2.0    Freq+ 拉满 ⇒ ÷3（0.13 秒）
    FREQ_GAIN_M  12.0    Freq- 拉满 ⇒ ×13（5.2 秒）；两侧刻意不对称，多人靠这一侧
    STEP_R        1.5    滑步判定阈值（局部单位，两脚中点位移）
    DEBUG_HUD       0    1 = 地板边画调试色带

  RF_FootRipple.fxsub 顶部：
    CONTACT_RATE  0.20   鞋底高度 / 小腿长 低于此算踩住（0.10 更灵敏 / 0.25 更迟钝）
    FOOT_THICK    0.22   踝骨到鞋底的高度（× 小腿长）
    FOOT_SLOTS    16     脚位槽数，须与 .fx 的 SLOT_MAX 一致
    CENTER_BUCKET 32.0   センター 的 XZ 粗桶（主判据）
    ROOT_BUCKET    8.0   全ての親 的 XZ 细桶（补判据）

  RIP_RADIUS 16 vs 地板 ±10 ⇒ 环会越过地板边缘再消失（约 3 秒到边）；
  地板放大（Si）时比例不变。


【控制器表情（RippleFloorCtrl.pmx）】

  全部 0 = 不改变；表情名精确匹配（ASCII、区分大小写，+/- 是名字的一部分）。
  缺失的表情读 0 ⇒ PMX 里可以分批加，不会报错也不会跑偏。

    Hue±      col = HsvToRgb(base.h + (P−M), base.s, base.v)        1.0 = 一圈
    Bright±   ×(1+2P) / ÷(1+2M)                                      ⇒ ×3 / ÷3
    Freq±     TriggerGap() = TRIG_GAP·(1+12M)/(1+2P)                  ⇒ 0.13s / 5.2s
    Life±     LifeMax()   = RIP_MAX·(1+2P)/(1+2M)                     ⇒ 15s / 1.7s
    Step±     StepLen()   = STEP_R·(1+2P)/(1+2M)                      ⇒ 4.5 / 0.5
    *Sz±      ShapeSize(type) = (1+1.5P)/(1+1.5M)                     ⇒ 2.5× / 0.4×
    Jitter    ShapeJitter(seed) = 1 + 0.25·J·(frac(seed)·2 − 1)       ⇒ 每条 ±25%
              seed = t0·7.31 + x·1.7 + y·2.9
              （必须混合落点：多人常同帧落地，只用出生时刻会同尺寸）
    Rot±      RotSpeed() = RIP_ROT·(1+1.5P)/(1+1.5M)                  ⇒ 10 / 1.6 rad/s
              （上限压 ×2.5：30fps 下约 10 rad/s 时五角星就到频闪边缘）

  形状尺寸只影响可见大小，不参与触发判据（判据只用落点），也不改寿命。


【调试色带（DEBUG_HUD = 1）】

  地板远边（-Z）会出现：
    A 带 16 小格  绿=这一帧在踩且上一帧也在踩；黄=刚落地；青=抬脚那一帧；黑=空中
    B 带 25 小格  队列各槽的年龄：白<1s / 黄<3s / 红<5s / 黑=空
    D 带  8 小格  每对模型的状态行：品红=读不到记录（行丢了/刚载入）/
                  绿=有记录且冷却已过 / 蓝=冷却中
    一条紫带      这一版真的被编译进去了（看不到 = MMD 还在用旧构建）

  「站着不动狂冒」的定位：先看 D 带，8 格全品红 = 状态行读不回来，
  滑步判定会每帧成立；再按上面 alpha 规则核对。


【构建与校验】

  编译（本机 fxc）：
    "C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0\x86\fxc.exe" ^
        /nologo /T fx_2_0 /Fo %TEMP%\rf.cso RippleFloorX.fx
    （.fxsub 同理）—— 只允许既有 X4121(ddx/ddy) 与 X4717(fx 弃用) 警告。

  编码纪律：.fx / .fxsub 是 Shift-JIS(CP932) + LF；readme / 本文档是 UTF-8 + LF。
  改 .fx 只要用 .NET 显式 CP932 读写，别用会改编码的 cmdlet。

  形状改动的验证（本机没有 MMD）：用 PowerShell + System.Drawing 按 shader 里
  **同一套数学**离线渲染 PNG 自检。必须逐项照抄阈值与常量，复现三角/方时记得
  乘 cos(π/n)（否则会画成外接半径 2×/1.41× 的巨框，图不可信）。

  ps_3_0 约束：常量寄存器已接近 c224，多加局部变量或表达式可能报
  X4507「maximum ps_3_0 constant register index (224) exceeded」。
  改完必须 fxc 验；超了优先复用现成量而不是新增。

  PMX（RippleFloorCtrl.pmx）追加表情的流程：
    1. 先探测**当前文件**的结构（别沿用旧偏移：用户可能用 PmxEditor 改过
       表示枠后重存，morph 尾部首字节会变）。
    2. 解析 header → 顶点 → 面 → 材质 → 骨骼 → morph 段；本文件的 morph 记录是
       「名 + 英名 + 19 字节尾部」。**尾部整段复制一条已在 MMD 里验证过的**（如
       Bright+），不要按 PMX 规范（type+count+payload）自己拼，实测对不上。
    3. 追加记录后，morph 数 +N；再把新条目加进「表情」表示枠（type=1 + 索引），
       该枠条目数 +N。
    4. 两条不变量必须同时成立（这就是校验）：
       ① morph 表走完的位置正好是「表示枠数」；
       ② 整个文件走完正好等于文件长度（不多不少）。
    5. 索引宽度都是 1 字节（顶点/材质/骨骼/表情/刚体）⇒ 索引 ≤127 才安全。


【版本史与教训】

  v1.x  脚位状态「读回 0」反复失败 → 曾误判为「.x 通道坏了」，实际是 alpha 规则。
  v2.0  定稿：掩码写满四通道读 .w；TEXTUREVALUE 取上一帧；触发只认落地沿。
  v2.1~2.3  多模型支持：16 脚位、模型对编号（センター 主判据 + 全ての親 补判据）。
  v2.4  节流改成按模型对（以前全场景共用一个，模型互相抢）。
  v2.5  队列扩到行 0-24（25 槽）。
  v2.6  加「滑步」判据（脚贴地滑没有高度沿）+ 每帧最多入队 8 条。
  v2.7  RIP_MAX / STEP_R 交给控制器表情。
  v2.8  滑步改用两脚中点（避免左右脚 ping-pong）。
  v2.9  **找到真因**：状态行的 alpha=0 ⇒ 整行读回 0；改成「一行 3 个 payload
        + .a 恒 1.0」，加了 ±40 的落点兜底与「滑步只在两脚都踩地时判定」。
  v3.0  加五角星 + 四种几何图案外接半径归一化。
  v3.1  加「花瓣爆开」（短命爆发），v3.2 因观感不搭删除。
  v3.3  尺寸（每图案 Sz±）与 Jitter 表情化。
  v3.4  五角星线宽按 |∂w/∂r| 补偿 + STAR_BAND_MUL。
  v3.5  旋转速度（Rot±）表情化。
  v3.6  Freq± 改成不对称增益（疏侧 ×13），公式抽成 TriggerGap() 供 HUD 共用。
